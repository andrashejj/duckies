# Sunset Duckies deployment

Deploy the club, members area, reservation shop, and admin panel as one Vercel Astro app. They share Better Auth sessions and one PostgreSQL database.

1. Provision a dedicated PostgreSQL database and set `DUCKIES_DATABASE_URL`, `BETTER_AUTH_URL`, `BETTER_AUTH_SECRET`, `RESEND_API_KEY`, and `EMAIL_FROM` in the target environment. `BETTER_AUTH_URL` must be the exact HTTPS origin. Add `EMAIL_ADMIN_NOTIFY` for shop alerts.
2. Install with `pnpm install --frozen-lockfile`; postinstall generates the Prisma query client without requiring a live database. The build command also generates it because Vercel can restore cached dependencies without rerunning postinstall.
3. With the target environment loaded, run `pnpm db:migrate` (`prisma migrate deploy`). It applies `prisma/migrations`, which create the auth, club, shop and branding tables. It does not seed products or assign access. A database that predates the baseline migration must first be marked: `pnpm exec prisma migrate resolve --applied 20260917000000_baseline`.
4. Approve an organiser with `pnpm member add you@example.com organiser`. Existing approved members use the same login for the shop and kids list.
5. Optionally run `pnpm db:seed` to add the three granola flavours as a draft drop (and retire any founding-kit apparel concepts still on the rack). Review them in `/admin` before setting the drop live.
6. Run `pnpm check` and `pnpm build`, then deploy using the existing Vercel workflow. For tests, use the separate `TEST_DATABASE_URL` described in README.md.
7. Verify the deployed `/shop`, a live product, guest reservation and receipt, customer email-code login, organiser administration, and unauthenticated rejection from `/api/kids`. Confirm actual email delivery with the configured sender.

Use a separate preview database and a stable preview origin. Never point preview tests at production. Public club content stays prerendered; authenticated API responses, order receipts, accounts, and admin pages disable browser/CDN caching. Private receipt links also disable referrer forwarding.

The legacy Auth.js/Google configuration is obsolete. Do not set `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET`, or `AUTH_SECRET` for this app. Do not use `DATABASE_URL`, `DIRECT_URL`, `prisma db push`, or the old `db:deploy` command. All runtime queries and the Prisma CLI use `DUCKIES_DATABASE_URL` (see `prisma.config.ts`); the checked-in migrations in `prisma/migrations` are applied by `pnpm db:migrate`.

If an old shop database contains real data, keep it intact. `pnpm db:migrate` refuses a database that still has the legacy uppercase `User` table. Review an export/import and user-ID mapping into the shared backend before switching traffic; this code change does not import or alter any live legacy database.

A family registering several children on one form requires `20260920080000_registration_multi_child`, applied with `pnpm db:migrate:production` before deploying the code that needs it: the new columns are read on every registration page load. It adds `signing_group` and `child_index` to `club_signed_waiver` — every record signed before it becomes a group of one, first in it, so existing waivers, PDFs and seals are untouched and `WAIVER_VERSION` does not move — and re-keys `club_registration_photo` on `(link_id, slot)` so each child on a form stages their own photo. The production database has been provisioned as `sunsetduckies-production` (Neon free plan, Frankfurt), and migrations 001–009 have been applied (through the plan board on 17 September 2026). Runtime credentials are configured on the Vercel production environment; keep preview and development disconnected from this database. The canonical auth origin is `https://www.sunsetduckies.com`. Migration commands should use the provider's unpooled connection, with `sslmode=verify-full`; runtime uses the pooled connection with the same TLS verification. The shop's founding catalogue is seeded as drafts for organiser review.

To apply a new migration to production, run it over the direct (unpooled) connection before pushing the code that needs it:

```bash
pnpm db:migrate:production
```

`scripts/db-target.ts` reads `PRODUCTION_DATABASE_URL` (and `STAGING_DATABASE_URL` for `pnpm db:migrate:staging`) from the local `.env`: the unpooled Neon URL with `sslmode=verify-full`. `pnpm db:status:production` reports pending migrations without changing anything. Code deploys from Git: `main` is production, `staging` is the staging preview. The Neon integration's other variables (`DATABASE_URL`, `POSTGRES_*`) are unused by the app.

`vercel.json` places the Node functions in Frankfurt alongside the database. Production deployments build from Git on Vercel; do not upload the locally built macOS Sharp binaries as a prebuilt Linux deployment.

The plan board (`/branding-plan/board`) and the `/branding-plan`, `/branding-plan/plan` and `/branding-plan/onsite` pages read the `plan_person`, `plan_milestone`, `plan_task` and `plan_task_event` tables (baseline migration). The baseline also pre-approves Estelle (niki.este.2022@ksz.edu-zg.ch) and Dori (onody.dora@gmail.com) as branding editors so they can sign in with the email code straight away. Milestones each carry one `due_on`; tasks move to do → doing → review → done. Milestones and tasks are seeded from `src/data/plan-tasks.ts` on the first approved read of an empty table; after that the database is the record and the seed file is history. Approved readers see the board; only editors can move tasks, reassign owners or add tasks, and each change checks the task version and records an event. Include the four `plan_*` tables in backups.

The Branding granola simulator uses the `granola_pack` and `granola_revision` tables (baseline migration). Apply it with `pnpm db:migrate` before deploying the simulator. Approved branding users can experiment and read shared recipes and version history; only those with edit access can save versions. Updates check the current version to prevent overwriting another editor, and the recipe plus history entry commit together. Include `granola_pack` and `granola_revision` in database backups. Starter mixes are code defaults until an approved editor first saves them; no existing club or shop records are changed.

The stored starter recipes are the three printed flavours — `the-og`, `dawn-patrol`, `power-up` (`20260918161000_granola_flavours` renames any recipe and history saved under the older `basic` / `sports` / `champ` ids, keeping a name the editors had already changed). Their pack cards show the pouch designs; a new granola type wears the blank "?" pouch until it has a design of its own. `20260918160000_granola_product_category` adds the `GRANOLA` product category the shop's granola drop uses. The baseline also allows arbitrary additional granola types. It preserves existing recipes and version history. New and duplicated recipes start as unsaved drafts in the editor; Save version persists them through the same editor-only API. Custom types use stable generated IDs, so renaming a recipe does not change its history or links.

Granola nutrition estimates work without external services. Optional per-ingredient nutrient values and serving size are saved inside the recipe JSON and its version history; older recipes remain readable. Generic references are USDA SR28 (2015), with source IDs in `src/lib/granola-nutrition-data.ts`. Missing nutrients remain unknown; baking yield is assumed to represent water loss. Estimates are for recipe planning, not a verified packaging label.

For the AI adviser, configure `OPENAI_API_KEY` on the server, then restart development or redeploy. Never expose the key through a public environment variable. `GRANOLA_AI_MODEL` optionally overrides the default `gpt-5-mini`; choose a Responses API model supporting structured outputs and low reasoning effort. The branding-editor-only, same-origin endpoint sends the current recipe, costs, nutrition and brief to OpenAI with `store:false`, validates suggestions and recomputes their effects locally. It does not save or apply a recipe automatically. Limits are shared in PostgreSQL (5 requests per minute and 30 per rolling day, per editor), including failed provider requests. An absent key shows “not connected”; nutrition and costing remain available. Integration tests intercept the provider with fixtures; a live provider smoke test requires a configured key.

Administrative birth-date corrections require `20260920160000_birth_date_corrections` before deployment. This additive migration stores an append-only correction against the original signed waiver, with the previous date, corrected date, reason, actor and time. Roster, Cup ages and re-signing prefills use the correction; saved PDFs and seals remain unchanged. A later guardian signature supersedes the correction. `pnpm exec tsx scripts/correct-birth-date.ts <private-json-file>` previews a correction; append `--apply` to record it. The JSON must contain `kidId`, `expectedDate`, `dateOfBirth`, `actorEmail` (an organiser) and `reason`. Load the intended database explicitly; keep real correction JSON outside Git.

Sunrise Duckies requires `20260926120000_club_sunrise_duckies` before deploying the code that reads `session_type`. It adds a `session_type` (`sunset`/`sunrise`) column to `club_training`, `club_attendance` and `club_attendance_event`, folds it into each table's primary key and foreign keys, and adds a `sunrise` rate to `club_point_rule` (defaulting to 5). Existing rows backfill to `sunset` and keep their points; nothing already recorded changes. The Training tab gains a Sunset/Sunrise picker next to the date picker, and **Point values** gains a Sunrise Duckies rate; a coach can now call both sessions for the same date, each earning its own points. Verify that switching the picker loads a separate roll and leaderboard total for the same date, that a duckie marked here in both sessions earns both point values, and that an organiser can set the Sunrise rate independently of Sunset's.
